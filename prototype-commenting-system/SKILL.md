# Prototype commenting system

A review layer that sits on top of an existing prototype without changing how the prototype works. Reviewers comment on the real thing, in place, and everyone sees the same comments.

The `examples/` folder holds a working reference implementation (vanilla JS client + Netlify Function on Netlify Blobs). It is a **baseline to adapt, not a file to paste**. Every project differs in how it decides "which screen is this", how it re-renders, and where it can store data, and those three things decide whether comments land in the right place. Spend your effort there.

## What a finished integration does

- Right-click (desktop) or long-press / comment mode (touch) on any element → "Comment" → name + text → a numbered pin anchored to that element.
- Pins follow their element through scrolling, resizing and re-renders, and only appear on the screen they were made on (same role/person, language, page, tab).
- A "Comments (N)" button lists every comment, marks ones made on other screens, and clicking one restores that screen, scrolls to the spot and opens it.
- Comments are stored in a shared backend, refresh for everyone without a reload, and can be deleted.
- The layer can't be broken by the prototype's CSS and doesn't break the prototype (Shadow DOM, capture-phase listeners, no changes to app markup required).

## Workflow

1. **Inspect the project before changing anything.** Work out:
   - Stack and build: single HTML file, bundled SPA (React/Vue/Svelte), multi-page site, several apps in iframes, per-role builds generated by a script.
   - Hosting, and what backend is realistic (Netlify, Vercel, Cloudflare, an existing API/DB, Supabase/Firebase, or nothing).
   - Navigation: hash routes, history routes, or in-memory state with no URL change at all.
   - Everything that changes what's on screen without changing the URL: role/person switchers, "preview as", language, site/tenant toggles, tabs, drawers, selected record.
   - Rendering: does it re-render often (React), virtualise lists, change layout responsively?
   - Whether a comment layer already exists (search for `contextmenu`, `data-cm-host`, `/comments`). If so, you are maintaining it: read it, don't replace it.
2. **Decide the integration point**: where the script goes so it loads on *every* screen and role that should take comments, and survives the project's build. Read `references/architecture.md`.
3. **Choose the backend.** Prefer what the project already has, and keep the same API contract whatever the store. Read `references/backend.md`.
4. **Define the screen context.** Write the adapter that says who/what is being previewed and which screen is showing. This is the step most likely to go wrong. Read `references/context-detection.md`.
5. **Adapt the frontend.** Start from `examples/frontend-example.js`. Adjust anchoring for the project's DOM, add the deep-link navigation hooks if the app has internal state, add touch input if reviewers use phones/tablets, and match colours if asked. Read `references/frontend.md`.
6. **Test it properly**: add, view, delete and navigate, across two browsers/users and on touch devices. Read `references/testing.md` and run the checklist on the deployed URL, not only locally.
7. **Report limitations** to the user in plain words, for example: no auth (anyone with the link can delete), iOS needs comment mode, comments made before a context change won't show, which screens couldn't be deep-linked.

## Principles

- **Adapt to the project, don't force the project to fit.** If the app already has an API, auth or a database, use it. If it's a React app, mount the layer once at the root rather than inside components.
- **Don't require changes to app markup to make anchoring work**, but use stable hooks where they exist (`id`, `data-testid`, `data-comment-anchor`): they are far sturdier than CSS paths.
- **A missing pin is better than a wrong pin.** If the element can't be found confidently, hide the pin and keep the comment reachable from the list.
- **Every app, role and page needs the layer.** In builds that produce several outputs, check each output contains it after every rebuild (the reference marks its host with `data-cm-host`).
- **Keep review notes out of the prototype's own UI**, and don't change the app's seed data or storage keys as part of adding comments.
- Ask before deploying to production or creating new hosted resources.

## Files

- `references/architecture.md`: components, data flow, data model, integration patterns per project type
- `references/frontend.md`: menu, composer, pins, anchoring, render loop, touch, styling, deep links
- `references/backend.md`: API contract, Netlify Function + Blobs, alternatives, security
- `references/context-detection.md`: building the screen context for roles, pages, language, tabs
- `references/testing.md`: functional, cross-user, cross-browser and device checklist
- `examples/frontend-example.js`: reference client (one IIFE, no dependencies, configured through `window.PROTO_COMMENTS`)
- `examples/comments.mjs`: reference Netlify Function (GET / POST / DELETE on Netlify Blobs)
- `examples/netlify/`: `package.json` and `netlify.toml` for the reference deploy
